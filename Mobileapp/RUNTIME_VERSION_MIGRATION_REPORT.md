# Runtime Version Migration Report

**Date:** 2026-06-09
**Author:** Platform Engineering
**Scope:** Nile Flow Mobile App (Expo SDK 56)

---

## Previous Strategy

```js
runtimeVersion: {
  policy: "appVersion";
}
```

The `appVersion` policy binds runtime version to the application version (1.2.8).
Every time the native app version is incremented, the runtime version changes.
This creates a 1:1 dependency between app store releases and OTA update eligibility.

## New Strategy

```js
runtimeVersion: {
  policy: "fingerprint";
}
```

The `fingerprint` policy computes a content-addressable hash of the native runtime
environment (metro config, native modules, assets, etc.). Only changes to native
binaries trigger a runtime version change. OTA updates can target all devices
sharing the same native binary fingerprint.

## Benefits

| Metric                     | `appVersion`           | `fingerprint`              |
| -------------------------- | ---------------------- | -------------------------- |
| OTA eligibility            | Per app version        | Per native build           |
| Store release independence | None                   | Full                       |
| Rollback granularity       | Coarse (version-level) | Fine (build-level)         |
| Update surface             | All OTA or none        | Selective per native build |
| CI/CD complexity           | Low                    | Low                        |

## Compatibility Analysis

- **Expo SDK 56:** Full support for `fingerprint` policy. Implemented via
  `@expo/fingerprint` CLI which ships with Expo SDK 56.
- **EAS Build:** Compatible. Fingerprint is computed during build and embedded
  into the native binary.
- **EAS Update:** Compatible. The fingerprint-based runtime version is matched
  during update retrieval.
- **Expo Go:** Not applicable. Development builds use their own fingerprint.

## Risk Assessment

| Risk                                               | Severity | Mitigation                                      |
| -------------------------------------------------- | -------- | ----------------------------------------------- |
| Fingerprint collision (same hash, different build) | Low      | Content-addressable SHA-256 prevents collisions |
| Fingerprint mismatch preventing OTA delivery       | Low      | Validate fingerprint during CI before publish   |
| Rollback complexity from fingerprint drift         | Medium   | Tag fingerprint with git SHA for traceability   |
| Developers unaware of fingerprint boundary         | Low      | Documented in operating model (Phase 8)         |

## Files Modified

- `Mobileapp/.env` — Removed `EAS_SKIP_AUTO_FINGERPRINT=1`
