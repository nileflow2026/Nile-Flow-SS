# 0002. Mobile checkout address confirmation

**Date**: 2026-10-04
**Status**: In Progress

## Summary

The Mobileapp will ask customers to select and confirm a saved delivery address before opening Payments. Customers can add an address or complete missing delivery details in the same step. The backend will verify address ownership, save a delivery snapshot, coordinate payment retries with a shared Redis lock (a shared temporary claim), and save provider updates in a durable inbox (a recovery record). Website2 and older app requests keep their current API behavior. After an app restart, the backend can restore an existing order and its saved address without storing address details on the device.

## Context

The Mobileapp currently moves from Cart to Payments without a confirmed delivery address. Its payment requests either omit the delivery address or send a placeholder. The address book already stores recipient names, phone numbers, and location details, but the mobile app does not connect that information to checkout.

This feature handles delivery personal information. Address documents currently receive public read access, address updates do not verify ownership, and the update service references an undefined database client. The checkout flow also needs to retain the selected delivery details on an order even if the customer later changes or removes the saved address.

The Mobileapp uses Expo Router, React Native, an existing cart context, authenticated REST endpoints, and Appwrite. Payment endpoints are shared with Website2 and older app versions. Mobile card orders are persisted by an Appwrite Function whose source is not present in this repository. The existing backend Redis client uses an in memory fallback when shared Redis is not configured. That fallback cannot coordinate payment retries across server instances.

The backend already defines a BullMQ payment reconciliation queue, but it has no worker. The M Pesa callback currently acknowledges processing errors, so provider redelivery cannot be relied on to recover missed payment updates.

> ⚠️ Premise note: Adding a confirmation screen without fixing address access would leave customer delivery details publicly readable. The feature therefore includes owner only address permissions and an existing record migration, not just a mobile interface change.

## Requirements

**User stories**:
- As a customer, I want to confirm where my order will be delivered before choosing how to pay, so that it reaches the right place.
- As a customer without a complete saved address, I want to add or complete one during checkout, so that I can continue without losing my cart.

**Acceptance criteria**:
- **AC-1**: Tapping Proceed to Checkout in the Mobileapp opens a delivery address confirmation modal before Payments. The modal contains address details only and does not ask for a payment method.
- **AC-2**: A signed in customer sees all saved addresses belonging to their account. The customer must select an address and explicitly confirm it before Payments opens.
- **AC-3**: If the customer has no saved addresses, the modal provides address entry. Recipient name, street address, and phone are required. City, region, postal code, and country are optional. The name is prefilled from the profile when available, remains editable, and country stays blank when omitted.
- **AC-4**: A newly entered address is saved through the existing address API, then selected for confirmation. Two saved addresses may have the same street text.
- **AC-5**: A saved address missing recipient name, street address, or phone can be completed and saved by its owner before confirmation.
- **AC-6**: Phone entry accepts local or international numbers with an optional leading plus sign. Spaces, hyphens, and parentheses are allowed for readability. Validation counts 7 to 15 digits and stores the trimmed value without changing its country code.
- **AC-7**: Address loading, adding, or updating failures keep the modal open, show an error, and allow retry. A failed address request is not shown as an empty address book, and checkout cannot continue without a complete saved address.
- **AC-8**: Cancel closes the modal and keeps the customer in Cart. The cart and any selected address remain available.
- **AC-9**: An unsigned customer is sent through the existing sign in flow and returned to Cart without losing the cart.
- **AC-10**: After confirmation, the selected address is held temporarily in the existing cart context, not in navigation parameters or persistent storage. Payments shows the confirmed delivery details and an Edit action before the first payment request creates an order. Edit opens the same selector and entry flow without losing cart contents or payment choices.
- **AC-11**: The delivery phone remains separate from any phone number entered for M Pesa payment.
- **AC-12**: The updated Mobileapp sends `addressConfirmationVersion: 1`, `deliveryAddressId`, and a stable `checkoutAttemptId` to cash on delivery, M Pesa, Pesapal, and mobile card payment order requests. On first order creation, version 1 requires a valid, complete address owned by the authenticated customer. The backend builds the order snapshot from the saved address, not client supplied address fields. Missing, deleted, incomplete, or unowned addresses, missing attempt IDs, and unsupported marker versions are rejected before order or payment creation. For a retry of an already created order, the backend uses the stored snapshot and verifies the order belongs to the authenticated customer.
- **AC-13**: New Mobileapp orders store `deliveryAddress`, `customerPhone`, `deliveryRecipient`, and `deliveryAddressId`. Locality fields are joined to `deliveryAddress` in the order `address`, `city`, `state`, `zipCode`, `country` order, omitting blank fields. The saved address ID is a reference only, not a database foreign key. The order snapshot stays unchanged if the saved address is edited or deleted.
- **AC-14**: Appwrite order fields added for this feature are optional at collection level for legacy orders, while the updated Mobileapp flow requires complete address details. Requests without `addressConfirmationVersion` from Website2 and older app versions retain their current behavior.
- **AC-15**: Address documents are readable, updatable, and deletable only by their owner. For existing documents, `user` is the owner when it is valid. Otherwise the legacy `userId` is used. If both fields identify different owners, public access is removed and the document is reported as conflicting. Documents without a usable owner lose public access and are reported for manual repair without guessing an owner or deleting the document.
- **AC-16**: Address list results include both current `user` ownership records and legacy `userId` ownership records without duplicates. Address create, update, and delete operations verify ownership on the server and accept only permitted address fields. Update and delete requests for addresses not owned by the customer return not found.
- **AC-17**: If a saved address lacks an owner, is deleted, or no longer belongs to the signed in customer at order creation, the order is rejected with an actionable error and the customer can return to address selection.
- **AC-18**: While the app remains active, the confirmed address stays in memory. After restart, the app uses the persisted checkout attempt ID to recover an existing order and its saved delivery snapshot and payment state from the backend. If no order exists yet, the app returns to address confirmation, requires the customer to select and confirm a complete saved address again, and reuses the attempt ID. A new provider payment may be started against an existing order after a definite failure or cancellation. The checkout attempt ID changes only when the customer abandons this checkout and starts a new one. Logout and account change clear the address and attempt state. Cart clear removes the address and clears the attempt ID only if no order exists or the customer has explicitly abandoned an order with a definitive terminal outcome. An existing pending or unknown order keeps its attempt ID for recovery.
- **AC-19**: Address and payment logs contain only operation, error category, payment status, and user or address IDs transformed with HMAC SHA 256 using the backend secret `LOG_ID_HASH_SECRET`. Logs do not contain raw IDs, request bodies, full names, addresses, phone numbers, provider references, access tokens, or other sensitive customer details.
- **AC-20**: A repeated version 1 request with the same user, address ID, and order contents returns the existing order and does not create a duplicate order. Reusing an ID with different order contents or a different address is rejected. Repeating the same provider initiation while its outcome is pending or unknown returns the existing payment state without starting another provider payment. After a definite provider failure or cancellation, another payment method or retry may start a new provider payment against the same order and checkout attempt ID. Concurrent version 1 payment mutations for the same attempt are serialized by the shared Redis lock. If another user submits an already used attempt ID, the request is rejected without disclosing the existing order. A new checkout attempt ID is used only when the customer abandons this checkout and starts a new one.
- **AC-21**: When a customer starts a new checkout, the app generates one globally unique UUID with `expo-crypto` and stores it under `checkoutAttemptId:<authenticatedUserId>` in existing AsyncStorage before sending the first payment request. It reuses the ID across provider changes, retries, and app restarts until order success or explicit abandonment. An attempt with no order may be abandoned at any time. Once an order exists, pending or unknown payment blocks abandonment; a new attempt ID is allowed only after a definitive terminal outcome. Cart clear may discard an attempt with no order, but must retain an existing order's ID while its payment is pending or unknown. The app blocks payment with a retryable error if storage fails. Address and phone remain in memory only and are restored after restart only from an authenticated backend order lookup when an order already exists. Logout and account change clear the prior account's key, and the app never reads one account's key while another account is active.
- **AC-22**: Once the first payment request creates an order, the address snapshot is locked for that order and Payments no longer allows address editing. A customer who needs a different address can start a new checkout only after the current payment outcome is definitively terminal. If no order exists, the customer can abandon the checkout and begin again with a new attempt ID.
- **AC-23**: After the authenticated account is restored, the app requests the order for the stored checkout attempt ID before starting another order or payment. The backend returns the order ID, stored item snapshot, amount, currency, order status, payment method and status, a normalized recovery state, and saved delivery snapshot only when the order belongs to the authenticated customer. It returns not found both when no order exists and when the attempt belongs to another customer. If no order exists, the app reopens address confirmation and retains the ID. If an order exists, the app restores its saved snapshot and payment state without reloading the current address book. Pending states resume without starting another payment. Unknown states trigger an authenticated status check through the existing M Pesa or Pesapal status endpoint; the backend reconciles and persists the provider result under the shared attempt lock. If the status remains unknown or the check fails, the app keeps payment blocked and offers another status check. Definite failure or cancellation allows a new payment against the same order. Successful and cash on delivery orders resume the existing order success flow and clear checkout state. Lookup failures remain visible and retryable and do not start a new order or payment.
- **AC-24**: After authentication and request validation, and before reading or changing order payment state, the backend acquires a shared Redis lock keyed by the checkout attempt ID for every version 1 payment mutation, including cash on delivery and provider status reconciliation. Callback workers acquire the same lock before changing order payment state. A lock held by another request returns HTTP 409 with code `CHECKOUT_ATTEMPT_BUSY`, without changing the order or starting a provider request. Missing `REDIS_URL` or unavailable shared Redis returns HTTP 503 with code `CHECKOUT_COORDINATION_UNAVAILABLE`, without changing the order or starting a provider request. Version 1 requests never use the in memory Redis fallback. The backend holds the lock while it reads and changes order or payment state. Provider paths persist the order with `payment_unknown` before calling a provider, then persist a definite result before releasing the lock. Cash on delivery persists the created order and its cash payment state before releasing the lock. Acquire atomically with `SET NX EX 120` and a unique token. Refresh every 30 seconds and release only when the stored token still matches, using an atomic ownership check for both operations. A refresh after expiry fails because the key no longer exists. A request that no longer owns the lock cannot write payment state or release the lock. Provider initiation requests have a 30 second timeout. If lock renewal or provider outcome is uncertain after provider initiation could have started, retain the unknown state and do not retry until an authenticated provider status check resolves it under a newly acquired lock. The checkout attempt lookup is read only and does not acquire this mutation lock.
- **AC-25**: For version 1 M Pesa and Pesapal orders, the existing provider callback routes normalize each callback and persist it in a service only Appwrite callback inbox before acknowledging it. Store provider name, event ID, provider reference, received time, and processing state. The attempt ID and order ID may be empty until the payment initiation request has saved its provider reference on the order. A periodic scanner associates unmatched events with orders once that reference is saved. Store normalized payment status, amount, and currency when available. For M Pesa, `ResultCode: 0` means success, a final nonzero result means failure, amount comes from callback metadata, and currency comes from the matched order. For Pesapal, status code 1 or description `COMPLETED` means success, status codes 2 or 3 or descriptions `FAILED`, `REVERSED`, or `INVALID` mean failure, known `PENDING` or `PROCESSING` states remain pending, and missing or unrecognized status means unknown. Pesapal amount and currency come from the existing provider status service. An explicit customer cancellation maps to cancelled. A provider timeout maps to unknown. Do not store the raw callback body or payment phone in the inbox. Enforce uniqueness on provider name and event ID. A repeated notification for a nonterminal event makes its existing inbox record eligible for another authoritative status check; it does not create a second record. After persistence, enqueue the event on the existing `nf:payment-reconciliation` BullMQ queue with job ID `payment-reconciliation:<inboxRecordId>`. The existing queue's ten attempts and exponential backoff with a five second initial delay apply. A periodic scanner starts with each backend worker and runs at least once per minute. It associates unmatched events with orders once their provider reference is saved and requeues persisted events still marked `received`, including failed queue jobs. After ten failed processing attempts, set `processingStatus` to `needs_review`, retain the event, and alert operators without logging payment details. Provide `Backend/scripts/replay-payment-callback-event.js` so an authorized operator can replay an event by inbox record ID. The worker acquires the same checkout attempt lock before validating the provider reference, amount, and currency and changing order payment state. It ignores stale events unless both the payment method and provider reference match the order's current payment. An amount or currency mismatch remains unknown and is marked for review. Duplicate callbacks and job retries are idempotent. If the lock is busy or Redis is unavailable, keep the event pending for retry. If inbox persistence fails, leave payment unknown and return a retryable provider failure response. The existing provider status services reconcile orders that remain unknown when callback persistence or delivery fails. Legacy callbacks keep their existing behavior.
  - Callback correlation uses the persisted order fields `mpesaCheckoutRequestID` and `pesapalTrackingId`. M Pesa `CheckoutRequestID` matches `mpesaCheckoutRequestID`. Pesapal `OrderTrackingId` matches `pesapalTrackingId`, and `OrderMerchantReference` matches the order number.
- **AC-26**: A backend flag `MOBILE_CHECKOUT_ADDRESS_CONFIRMATION_V1_ENABLED` controls new version 1 order and payment starts. When false, those requests return HTTP 503 with code `CHECKOUT_FEATURE_UNAVAILABLE`, without falling back to legacy handling. Lookup, provider status reconciliation, and callback processing remain available for existing version 1 attempts. Requests without the version marker retain their current behavior. Enable the flag only after the order schema, callback inbox, shared Redis, queue worker, and scanner are ready. During rollback, disable new version 1 starts but keep recovery, status checks, and callback processing enabled until every existing attempt is terminal.

## Options considered

### Address confirmation: Confirm in Cart and reuse the same selector in Payments

Open a native modal from Cart, use existing saved address APIs, keep the selection in memory, and show the same selector from the Payments Edit action. Existing payment requests receive an address ID and the backend resolves it for the order.

**Pros**:
- Matches the requested point in the customer journey.
- Reuses the existing address book and payment screen.
- Avoids a new navigation route, address endpoint, or extra server request.
- Keeps personal details out of navigation parameters.

**Cons**:
- Requires coordinated mobile, backend, Appwrite, and card function changes.
- Requires a safe migration of existing public address permissions.
- Card payment work depends on the function source being made available.

### Option 2: Add a separate address selection screen

Navigate from Cart to a dedicated address page, then continue to Payments after selection.

**Pros**:
- Gives address management more room as it grows.
- Separates address selection from the cart interface.

**Cons**:
- Adds navigation and more ways for checkout state to be lost.
- Does not match the requested confirmation modal.

### Option 3: Send address text from the client without resolving an address ID

Send the selected name, address, and phone directly in each payment request, without linking the request to an owned saved address.

**Pros**:
- Requires fewer address lookups on the backend.
- Can work with clients that do not use the address book.

**Cons**:
- The backend cannot prove that the address belongs to the customer.
- Client supplied values can be stale or changed before order creation.
- Orders cannot reliably refer to the selected saved address.

### App restart recovery options

1. Persist the full delivery address on the device. This restores the screen directly, but keeps personal address data in local storage and can leave it stale.
2. Persist the attempt ID only, then resolve an existing order and its saved snapshot from the backend. If no order exists, ask the customer to confirm an address again.
3. Persist the address document ID and reload it from the address book. This cannot restore a deleted or changed address after an order is already created.

**Recommended**: Option 2. It keeps address details off the device, restores the immutable order snapshot, and uses the address confirmation flow only when no order exists.

### Payment retry coordination options

1. Keep only the order state check and unique order index. This needs no additional runtime service, but two requests can both observe a failed order before either changes its state and start separate provider payments.
2. Add Appwrite lock records. This uses the existing database, but adds a collection and requires recovery for records left by a crashed server.
3. Use an atomic lock in shared Redis and refuse version 1 payment requests when Redis is unavailable. This works across backend instances and uses an existing dependency, but payment initiation depends on configured shared Redis.

**Recommended**: Option 3. The order index protects order creation but cannot serialize retries against an existing order. The Redis lock coordinates the full payment decision across server instances, and refusing to use the in memory fallback avoids unsafe success shaped behavior.

### Provider callback delivery options

1. Update payment state directly inside the callback request. This is simple, but a callback can be lost if the service fails and can race with a payment initiation request.
2. Save a normalized callback event durably, then process it under the checkout attempt lock. The callback can be acknowledged once saved, and a worker can retry after process or Redis failures.

**Recommended**: Option 2. The current M Pesa callback acknowledges even when processing fails, so provider redelivery cannot be the recovery mechanism. The Appwrite inbox is the durable source, while the existing BullMQ payment reconciliation queue gives near immediate processing and a periodic scan recovers missed jobs.

## Decision

**Address confirmation**: Confirm in Cart and reuse the same selector in Payments.

The Mobileapp will use a reusable native address confirmation modal, keep the selected address temporarily in the existing cart context, and send only its ID to payment APIs. The backend will resolve the ID for the authenticated customer and persist the delivery snapshot. The app persists only the checkout attempt ID. On resume, an authenticated backend lookup restores the saved delivery snapshot and payment state for an existing order; if no order exists, the customer confirms an address again. Existing clients that omit the version marker will retain their current behavior.

For restart recovery, the Mobileapp calls the authenticated checkout attempt lookup with the locally stored attempt ID. The backend returns the matching customer's existing order and saved snapshot, or not found if no owned order exists. Not found reopens address confirmation with the same attempt ID. The order and address data never come from local storage.

**Restart recovery**: Use the attempt ID stored under `checkoutAttemptId:<authenticatedUserId>`. Generate a globally unique UUID with `expo-crypto` when the customer starts a new checkout. Persist it before the first payment request. Reuse it across network retries, app restarts, and payment methods until order success or the customer abandons the checkout after a terminal outcome. The Orders collection is the only server record of an attempt; no separate attempt collection is added. The first successfully persisted order binds that ID to its owner, address, and order contents. A request with the same ID but different owner, address, or order contents is rejected without revealing the existing order. If no order exists, the ID is not yet bound and can be reused after the customer confirms an address again.

**Payment retry coordination**: Use one Redis lock for each globally unique `checkoutAttemptId`, shared by cash on delivery, M Pesa, Pesapal, mobile card payment requests, and version 1 payment callback workers. Acquire it with an atomic set only when absent, a 120 second expiry, and a unique ownership token. Refresh it every 30 seconds while the request is active. Refresh and release use an atomic ownership check so an expired lock owner cannot change or delete a newer owner's lock. A busy lock returns HTTP 409 with `CHECKOUT_ATTEMPT_BUSY`. Missing `REDIS_URL` or a Redis error returns HTTP 503 with `CHECKOUT_COORDINATION_UNAVAILABLE` before order or payment state changes. Do not fall back to the in memory Redis client. Persist an unknown payment state before calling a provider, and save an accepted, failed, or cancelled state before releasing the lock. Cash on delivery saves the order and cash payment state while holding the lock. Provider initiation requests time out after 30 seconds. If Redis ownership or the provider outcome becomes uncertain after a provider call could have started, retain the unknown state and block retries until authoritative payment status is resolved.

**Provider callback delivery**: Save normalized M Pesa and Pesapal callback events to a service only Appwrite inbox before acknowledging the provider. Process them through the existing BullMQ payment reconciliation queue under the same attempt lock. A periodic scan requeues records that are not processed, so the inbox remains the recovery source if Redis, the queue, or a backend process is unavailable. Validate callbacks against the active provider payment reference, order amount, and currency. Keep legacy callback handling unchanged.

## Rationale

The callback inbox is necessary because the existing M Pesa handler acknowledges callbacks even when order processing fails. Persisting a normalized event before acknowledgement avoids depending on provider redelivery. The Appwrite record survives backend restarts and Redis outages; BullMQ provides prompt processing, and a periodic scan recovers records that were saved but not queued.

The existing AddressService and authenticated address endpoints already support listing, adding, updating, and deleting customer addresses. Reusing them keeps this change within the current Mobileapp and backend architecture. An in memory context avoids putting personal delivery details in navigation parameters or persistent storage. The attempt ID provides a lookup key after restart. The backend can return an existing order's immutable snapshot, while a checkout that did not create an order asks the customer to confirm an address again.

The backend must resolve the address because payment requests are untrusted. Storing a snapshot protects order history from later address edits or deletion. Optional Appwrite fields and conditional backend behavior preserve older records and existing Website2 callers. Card orders can only meet the same contract after the separately deployed Appwrite Function source is available.

The unique attempt index cannot serialize a retry against an existing order. Two server instances can both observe a failed payment before either writes the next state. A shared Redis lock makes that decision atomic across instances. The existing in memory fallback is deliberately excluded because it cannot coordinate production servers. The cost is that updated Mobileapp payment requests stop safely when shared Redis is unavailable.

**State transitions**:

`closed` → `loading addresses` → `selecting or entering address` → `saving address` when needed → `confirmed` → Payments. A load or save failure returns to the selector with an error. Cancel returns to Cart. The address can be edited until the first payment request creates an order. After that, the order snapshot is locked; payment failure or cancellation retains the confirmed address and checkout attempt ID for retries. On app resume, an existing attempt loads the order from the backend. An existing order restores its snapshot and payment state; not found returns to address confirmation with the same attempt ID; a lookup failure stays in a retry state. A new checkout with a different address can begin only after a terminal payment outcome. Order success clears checkout state. Cart clear discards the attempt only when no order exists or an existing order has a definitive terminal outcome; pending or unknown orders retain the ID for recovery.

An attempt with no order may be abandoned at any time because no payment has started. Once an order exists, pending or unknown payment blocks abandonment; the customer may abandon and start a new checkout only after a definitive terminal outcome. Successful orders resume their success flow and clear checkout state.

Address API success responses keep the current shape: the list is a raw array, create and update return the saved Appwrite document, and delete returns 204 with no body. Error responses keep the existing `error` property and add the stable `code` shown in the table. `ADDRESS_NOT_FOUND` is identical for an absent address and an address owned by someone else. Checkout and payment endpoints use `{ success: false, code, message }`; `CHECKOUT_ATTEMPT_NOT_FOUND` has the same status and response for an absent or unowned attempt. A provider initiation timeout returns HTTP 202 with `success: true`, the persisted order ID, `paymentStatus: "unknown"`, and `recoveryState: "payment_unknown"`, so the app checks status instead of starting another payment.

The compatibility contract is strict. Requests without `addressConfirmationVersion` use the existing behavior for Website2 and older app versions. Version 1 requests require `deliveryAddressId` and `checkoutAttemptId`; the backend rejects missing values, unsupported versions, invalid addresses, and incomplete addresses. Missing or unsupported version 1 fields return HTTP 400 with `INVALID_CHECKOUT_REQUEST`. Missing, deleted, unowned, or incomplete addresses return HTTP 404 `ADDRESS_NOT_FOUND` or HTTP 400 `INVALID_ADDRESS`, as applicable. Reusing an attempt ID with a different owner, address, or order contents returns HTTP 409 `CHECKOUT_ATTEMPT_CONFLICT` without exposing another customer's order. Version 1 requests ignore client supplied delivery snapshots and never fall back to legacy behavior. For new Mobileapp address creation, the app sends `country: ""` when the customer leaves country blank, and the backend preserves it. Legacy clients that omit `country` retain the current Kenya default.

Every version 1 payment mutation acquires the same lock for its checkout attempt after authentication and request validation, before reading or changing order payment state. A lock held by another request returns 409 with `CHECKOUT_ATTEMPT_BUSY`, without starting a provider request or changing the order. Missing `REDIS_URL` or a Redis error returns 503 with `CHECKOUT_COORDINATION_UNAVAILABLE` and does not fall back to the in memory client. Before provider initiation, persist `payment_unknown`; after the provider response, persist its definite state before releasing the lock. For cash on delivery, persist the order and cash payment state while holding the lock. Acquire with an atomic `SET` using `NX` and `EX 120`, refresh with an atomic ownership checked operation every 30 seconds, and release with an atomic ownership checked delete. Set provider request timeouts to 30 seconds. If the provider call could have started and its outcome or lock ownership is uncertain, keep the order unknown and do not retry until the payment status is authoritatively resolved. The authenticated status lookup is read only and does not acquire this lock.

Lock errors use the existing structured API response format: `{"success": false, "code": "CHECKOUT_ATTEMPT_BUSY"}` for HTTP 409, and `{"success": false, "code": "CHECKOUT_COORDINATION_UNAVAILABLE"}` for HTTP 503. The ownership token is a unique UUID generated with Node's built in `crypto.randomUUID()`.

The rollout flag `MOBILE_CHECKOUT_ADDRESS_CONFIRMATION_V1_ENABLED` defaults to false. While it is false, new version 1 order and payment starts return HTTP 503 with `CHECKOUT_FEATURE_UNAVAILABLE`. Lookup and recovery for existing attempts, provider status checks, callback ingestion and processing, and legacy requests remain available.

For version 1 M Pesa and Pesapal callbacks, first persist a normalized event in the service only inbox. Then enqueue its stable event job and acknowledge receipt. If enqueueing fails after persistence, acknowledge receipt because the event is durable; the periodic scanner will enqueue it again. The worker uses the checkout attempt lock, validates the event against the order and provider, applies the payment transition, and marks the event processed. A lock conflict, Redis outage, or transient Appwrite failure leaves the event available for a later retry. If inbox persistence itself fails, return a provider failure response rather than reporting success. Existing callback behavior remains unchanged for legacy orders.

The mobile card path also writes through the Appwrite Function identified by `ORDER_FUNCTION_MOBILE_ID`. Its source is not in this repository. The backend passes the server resolved snapshot and `checkoutAttemptId` to the function. The function uses the attempt ID to deduplicate order writes and confirms a saved order before the backend creates a Stripe payment intent. A repeated order request returns the saved order without creating another order. A repeated Stripe initiation while its outcome is pending or unknown returns the existing payment state; after a definite failure or cancellation, the same order can receive a new provider payment. The backend must not treat accepted execution submission as proof of order persistence.

The checkout attempt lookup returns the persisted order item snapshot, amount, currency, order status, saved delivery snapshot, authoritative payment method and status, and a normalized `recoveryState`. `orderId`, `items`, `amount`, `currency`, `orderStatus`, `paymentMethod`, `paymentStatus`, `recoveryState`, and the four delivery fields are required for version 1 orders. The order document is authoritative for the item snapshot, amount, currency, order status, and delivery snapshot. Its persisted payment fields, updated by the existing payment handlers, callback worker, and status reconciliation endpoints, are authoritative for payment method and status. Map `initiated` or `pending` to `payment_pending`, `unknown` or missing or unrecognized status to `payment_unknown`, `failed` to `payment_failed`, and `cancelled` to `payment_cancelled`. Map a succeeded payment with successful order status to `order_succeeded`; map cash on delivery to `cod_order_created`. For M Pesa, `ResultCode: 0` or an authoritative successful status means succeeded; other final provider results mean failed. For Pesapal, status code 1 or description `COMPLETED` means succeeded; codes 2 or 3 or descriptions `FAILED`, `REVERSED`, or `INVALID` mean failed; known `PENDING` or `PROCESSING` states mean pending; missing or unrecognized states mean unknown. A provider timeout is unknown, never a failure. An explicit customer cancellation maps to cancelled. The endpoint checks the authenticated owner before returning any order or delivery details. An absent or unowned attempt returns the same not found response. It does not return payment credentials or provider secrets.

The app uses `recoveryState` to resume. `payment_pending` and `payment_unknown` restore the current state and block a second provider initiation. `payment_failed` and `payment_cancelled` allow a new provider initiation against the same order. `order_succeeded` and `cod_order_created` resume the existing order success flow and clear checkout state. Any unrecognized or missing payment status maps to `payment_unknown`, so it cannot start a new payment. A lookup server or network failure is never treated as not found.

**Key invariants**:

- The updated Mobileapp cannot open Payments until a complete saved address has been explicitly selected and confirmed.
- Only the address ID crosses the payment API boundary from the updated Mobileapp. The server creates address snapshots from an owned saved record.
- A new order request with `addressConfirmationVersion: 1` cannot create an order without a valid, owned delivery address.
- A payment request with version 1 also requires a stable checkout attempt ID. Repeating that request for the same customer and checkout returns the same order without creating another order. The ID is shared across payment methods.
- A repeated order request must match the existing order's customer, address ID, and contents. A mismatch is rejected; it cannot replace the saved order snapshot.
- Repeating a provider initiation while its result is pending or unknown returns its existing state without starting another payment. A new provider payment after a definite failure or cancellation uses the same order and checkout attempt ID. Provider transaction identifiers and status determine whether an initiation is a retry or a new payment.
- Concurrent version 1 payment mutations with the same attempt ID are serialized by the shared Redis lock. The unique attempt index remains a final guard against duplicate order creation. If order creation races, the backend reads and returns the existing order only after confirming that it belongs to the authenticated customer.
- The app persists the attempt ID before sending a payment request. If local storage fails, it displays a retryable error and does not start payment. Only the attempt ID is persisted; address and phone details remain in memory.
- On app resume, an existing attempt ID is resolved through the authenticated checkout attempt lookup before another order or payment request is sent.
- The attempt ID is a globally unique UUID, while the local storage key includes the authenticated user ID. The app reads only the current account's key and clears it on logout or account change.
- The Orders collection is the only server record of an attempt. Its unique attempt index prevents concurrent requests from creating more than one order. No order means the ID is not yet bound to address or cart contents.
- The order record is authoritative for its immutable item, amount, currency, delivery, and order status fields. Its persisted payment fields are authoritative for the payment method and status used during recovery.
- The backend returns a required normalized recovery state. Pending or unknown blocks duplicate initiation, failed or cancelled allows a new provider attempt against the same order, and succeeded or cash on delivery resumes order success.
- If lookup finds an order, its stored snapshot is the source of the restored address and the current address book is not consulted for that order.
- If lookup returns not found, no order has been created for that attempt. The app requires address confirmation again and keeps using the same attempt ID.
- A checkout with no order may be abandoned at any time. If an order is pending or unknown, cart clear cannot discard its attempt ID; abandonment is allowed only after a definitive terminal outcome.
- The lookup returns the same not found response for absent and unowned attempts, and never returns another customer's order or address details.
- Two devices recovering the same attempt for the same owner receive the same order and state. Concurrent payment initiation still follows AC-20 and cannot start a second provider payment while the first is pending or unknown.
- A version 1 provider callback is not acknowledged until its normalized event is durably saved. Callback events are processed under the same attempt lock, and repeated delivery or job execution cannot apply a payment transition twice.
- Callback processing verifies the current provider transaction reference and order amount and currency. A stale callback from an earlier failed provider attempt cannot overwrite the current attempt's payment state.
- If the local attempt key is missing, the app does not replay a prior payment request. A fresh attempt ID is generated only after the customer explicitly starts a new checkout. Existing orders remain accessible through the existing Orders flow.
- A lookup network or server error is not treated as not found. The app keeps the attempt ID, shows an error, and offers retry without starting payment.
- Requests from existing clients without `addressConfirmationVersion` preserve their current behavior.
- An address ID selected by the customer is represented by the Address `$id`, not by its visible street text. The selector shows recipient, location, and phone so duplicate street text remains distinguishable.
- One checkout readiness rule applies in the app and backend: `fullName`, `address`, and `phone` must be nonempty after trimming. Locality fields are optional.
- Before order creation, a saved address edited after selection is revalidated by ID before payment. A deleted, incomplete, or unowned record clears the current selection and requires reselection. Once an order exists, retries use its stored snapshot and do not depend on the current saved address.
- The address may be edited before order creation. Once created, the server owned order snapshot does not change and Payments disables address editing for that checkout. A different delivery address requires a new checkout after the payment outcome is definitively terminal.
- The new Mobileapp sends an explicit empty country value when country is omitted from the form. The legacy Kenya default applies only when a legacy caller omits the country field.
- New delivery snapshots are never silently truncated to fit an Appwrite string attribute. The migration must ensure the existing `deliveryAddress` field can hold the composed value.
- Appwrite address permissions never grant public reads after the privacy migration.
- An order snapshot does not change when its source address changes or is deleted.
- No country is invented when a customer leaves it blank.
- The delivery phone never replaces the payment phone.
- Address API errors remain distinguishable from an empty address list.

**Security model**:

All address operations require the existing JWT. The backend derives the owner from `req.user.userId`, verifies ownership before update, delete, or order use, and restricts update inputs to approved address fields. The checkout attempt lookup also requires the JWT and returns order and address details only after checking the order owner; unowned and missing attempts return the same not found response. Appwrite Address documents grant read, update, and delete permissions only to their owner. Callback inbox documents grant access only to the backend service identity. If `user` and `userId` disagree, the record is treated as unresolved. The permission migration removes public access from unresolved records and reports document IDs with reason codes for manual repair. Update and delete return not found for a record not owned by the caller. Structured logs allow only operation, error category, payment status, and hashed user or address IDs. No payment or Appwrite Function path logs request bodies, callback payloads, or raw personal details. Existing order and payment authorization remains in place.

**Configuration required**:

- `REDIS_URL`: Shared Redis for locks and BullMQ, reachable by every backend instance. Version 1 payment starts fail closed if it is missing or unavailable.
- `APPWRITE_PAYMENT_CALLBACK_EVENTS_COLLECTION_ID`: Service only Appwrite inbox for normalized M Pesa and Pesapal callback events.
- `MOBILE_CHECKOUT_ADDRESS_CONFIRMATION_V1_ENABLED`: Explicit rollout gate, false until the schema, shared Redis, worker, and scanner are ready.
- `LOG_ID_HASH_SECRET`: Random backend secret used to HMAC SHA 256 hash user and address IDs in logs. Do not reuse a JWT, Appwrite, or payment provider secret.

The existing BullMQ payment reconciliation queue uses the shared Redis connection. Legacy requests without the version marker keep their current behavior. Appwrite database, address and order collection IDs, backend service credentials, and JWT configuration remain as currently configured.

## Consequences

**Positive**:
- Customers confirm a real delivery location before payment.
- Every updated Mobileapp payment method can create an order with a consistent server verified delivery snapshot.
- Existing addresses and orders remain usable, and old orders do not need a backfill.
- Address information is no longer publicly readable in Appwrite.

**Negative / tradeoffs**:
- The feature spans the Mobileapp, backend payment paths, Appwrite attributes, and address permissions.
- Card payment support cannot be completed until the Appwrite Function source is available.
- Ownerless address records become inaccessible through direct Appwrite reads after public access is revoked, and need manual review.
- The existing address update route needs a security and reliability fix before it can support checkout completion.
- Unique attempt storage and provider response checks add work to payment paths, but prevent duplicate orders and payment initiation on network retries.
- Updated Mobileapp payment requests require shared Redis. When it is unavailable, checkout initiation fails closed rather than risking concurrent provider charges. An uncertain provider timeout can leave payment unknown until its authoritative status is resolved.
- Callback processing adds a service only Appwrite collection and a reconciliation worker. The durable inbox allows provider callbacks to be acknowledged before payment state is changed, and remains the source of truth if Redis or BullMQ is unavailable.
- Events that fail ten processing attempts require operator review and an explicit replay. Their orders stay unknown until status is reconciled, so customers cannot start another payment prematurely.

**Neutral**:
- Website2 and older app payment requests without an address ID keep their prior behavior.
- `expo-crypto` is added for UUID generation, an authenticated endpoint is added for checkout recovery, `APPWRITE_PAYMENT_CALLBACK_EVENTS_COLLECTION_ID` configures the callback inbox, `MOBILE_CHECKOUT_ADDRESS_CONFIRMATION_V1_ENABLED` controls rollout, `LOG_ID_HASH_SECRET` protects log identifiers, and the existing `REDIS_URL` must point to shared Redis for version 1 payment requests and reconciliation.
- Existing order documents keep the new attributes empty; only new version 1 Mobileapp orders use them.
