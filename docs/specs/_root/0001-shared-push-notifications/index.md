# 0001. Shared mobile push notifications

**Date**: 2026-10-06
**Updated**: 2026-10-08
**Status**: In Progress

## Summary

This decision gives Nile Flow one reliable route for mobile push alerts and adds an admin broadcast tool. The Backend will use Expo and the existing Redis queue, while Appwrite stores campaign records, delivery progress, and user preferences. Customers can choose push categories and sounds, and admins can review honest delivery results without seeing recipient identities.

## Requirements

**User stories**:

* As a customer, I want important order and account changes to reach my phone so that I can act without repeatedly opening the app.
* As a customer, I want to control push categories and sounds separately so that I can choose which alerts reach my device and how they sound.
* As an admin, I want to compose, preview, send, and review mobile broadcasts so that customers receive timely promotions and service information.

**Acceptance criteria**:

* **AC-1**: On supported Android and iOS builds, a signed in user who grants operating system notification permission has an Expo push token registered to their authenticated user record. A missing permission or token is not reported as successful registration. Transient registration failures are logged and retried when the app becomes active.
* **AC-2**: Automatic mobile pushes use one centralized Expo delivery path backed by the existing `nf:notifications` BullMQ queue. The same event must not also send an Appwrite Messaging push. Existing email, SMS, WhatsApp, and in app behavior outside the push path remains intact.
* **AC-3**: Customers receive one normalized confirmation intent for a successful online payment, or an accepted cash on delivery order, followed by pushes for later changes to preparing, ready for dispatch, out for delivery, delivered, cancellation request received, and cancellation approval or rejection. If payment acceptance and order confirmation happen in the same Backend operation, they produce one normalized confirmation intent, not two. The later completed state does not create another delivery notice. New accounts created after rollout receive one welcome push after their first authenticated device registers. Successful password and email changes send security pushes when a token is registered. Security and welcome pushes cannot be disabled in the app. Replayed events with the same event key do not create another push during the one year event receipt retention period. Expo and Appwrite cannot commit atomically, so a recovered pending receipt whose prior provider acceptance was not saved can produce a duplicate push; delivery is at least once, not exactly once.
* **AC-4**: The existing Mobileapp Notification Settings panel exposes promotional push consent. The first choice is off for existing and new users. Turning it on requests operating system permission when needed and explains that a registered token is also required. Turning it off prevents future promotional campaign push delivery, but does not remove its in app notice. Order and service alerts remain independent. When the app resumes and notification permission has been revoked, it unregisters the device token without prompting again. Logging out also unregisters the token.
* **AC-5**: AdminDashboard adds a Broadcasts tab to its existing Notifications page. Admins can compose a promotion, app update, or service announcement with a required title of at most 80 characters, a required body of at most 240 characters, and an optional allowlisted in app destination. A preview shows these values, the Backend calculated in app audience estimate, and the push eligible estimate. The final confirmation distinguishes the two counts, including when a campaign will create in app notices but send no pushes. Scheduling is not included.
* **AC-6**: The campaign snapshot includes users whose first push token registration is no later than the saved snapshot time, regardless of current token presence, category preference, or marketing consent. Before expiry, the worker creates an owner scoped in app notice for each snapshot user. It attempts push delivery only when that user currently has a token and the relevant category push setting is enabled. Promotion pushes also require `marketingPushEnabled` to be true. App update and service announcement pushes do not require marketing consent. A disabled category or withdrawn consent skips only the push, not the in app notice. The Backend refuses campaign creation when the current in app audience estimate is zero. If the final snapshot becomes empty after preview, the campaign completes with a zero target and sends nothing.
* **AC-7**: Each send is an idempotent operation. Repeating a request with the same admin and `Idempotency-Key` returns the same campaign, and must not create duplicate pushes or in app records. A different payload with the same key is rejected.
* **AC-8**: Campaign processing is asynchronous and durable. The API returns HTTP 202 only after a new campaign is saved and its work is accepted by the queue. If the record is saved but queue acceptance fails, the API returns HTTP 503 with the saved campaign ID and an explicit not queued result. An idempotent replay returns the saved campaign with its current status, without creating another send. The campaign records are the source of truth, and a recovery worker requeues pending work after a process or enqueue failure. It resumes from the saved cursor, drains pending delivery rows before moving to another page, and recovers a `sending` campaign when its deterministic queue job is missing or failed. When durable Redis is unavailable, the API does not claim that work was queued.
* **AC-9**: Campaign results distinguish the preview estimates from the final targeted count. At preview time, the in app audience estimate counts users with a recorded `pushTokenFirstRegisteredAt`; the push audience estimate counts the subset with a current token and eligible category settings and consent. The final snapshot includes users whose first push token was registered by the saved snapshot time, including candidates that later prove ineligible for push and are counted as skipped. Promotion push delivery requires current consent and a consent timestamp no later than the snapshot time. Final push counts include accepted by Expo, rejected, unresolved, and skipped recipients, and add up to the final targeted count. Separate in app counts show created, unresolved, and skipped notices, and add up to the same target when recipient processing is complete. Pending push and in app work is derived from each target minus its terminal outcomes. Before audience preparation finishes, the interface shows that the recipient snapshot is being prepared rather than showing pending counts. The interface explains that Expo acceptance does not prove a device displayed the notification.
* **AC-10**: Campaign history is paginated, newest first by creation time and then document ID, with a default page size of 20 and maximum of 100. Summaries show campaign ID, title, category, status, creation time, both estimates, final target when available, in app created, unresolved and skipped counts, push outcome counts, and pending counts when available. Detail shows content, category, lifecycle status, timestamps, estimates, actual target, and aggregate results only. It never exposes recipient names, IDs, or push tokens. While queued or sending, an open detail refreshes every 5 seconds and stops when processing ends.
* **AC-11**: A campaign can be cancelled only while queued and before recipient processing starts. Cancellation and worker start use the same Redis campaign lock, so exactly one transition wins. A queued cancellation creates no recipient rows or in app notices. A campaign retry action processes only confirmed transient failures, never accepted or ambiguous deliveries. The Backend classifies HTTP 429 and 5xx responses and Expo `MessageRateExceeded`, `MessageServerUnavailable`, and `InternalServerError` as transient. `DeviceNotRegistered` and other explicit ticket errors are permanent; network timeouts without a ticket are ambiguous. Automatic retries are limited to five attempts. An admin may retry a confirmed transient failure once, with up to five additional attempts. Repeating a retry while its delivery rows are already pending does not enqueue another copy. Counts show each recipient's latest state, not cumulative attempts. Ambiguous failures are reported unresolved and cannot be manually retried. Event recovery retries a pending receipt when Expo may have accepted a push but the Backend did not save the result. A small duplicate risk is accepted for that timeout or worker crash case.
* **AC-12**: Promotion pushes expire 24 hours after campaign creation, app update pushes expire after 30 days, and service announcement pushes expire after 7 days. The Backend saves each campaign's immutable `expiresAt` deadline at creation. Before creating an in app notice or attempting a push, the worker skips and counts a recipient if the deadline has passed. Otherwise, it creates the in app notice, then passes the remaining lifetime to Expo. If a push retry or recovery attempt occurs at or after expiry, it marks the delivery skipped and does not resend, but retains any in app notice created before expiry. Expired, opted out, or otherwise ineligible recipients are skipped and counted. A queued campaign cancelled before processing creates no recipient rows or notices. All automatic event pushes expire after 7 days.
* **AC-13**: A push tap opens the validated in app destination when present, otherwise the existing notification list. Foreground pushes continue to show a banner and notification list. The selected category sound is used unless the category is set to silent or the synced master mute is on. Android channel settings remain under operating system control.
* **AC-14**: Every campaign action and user preference update is authorized on the Backend. Only an authenticated user whose Backend role is exactly `admin` can preview, send, list, view, cancel, or retry campaigns. A customer can only read or change their own promotional consent, category push settings, sound choices, and master mute. Campaign and delivery collections are private to the Backend service.
* **AC-15**: Campaign delivery records and automatic event receipts never copy raw push tokens or message bodies. Logs exclude tokens and user level delivery data. Invalid device tokens are removed from the user record. Detailed campaign delivery records and compact automatic event receipts are deleted after one year; campaign content and aggregate counts remain.
* **AC-16**: Production Android and iOS builds are verified on supported devices after Firebase client configuration and EAS FCM and APNs credentials are checked. The verification confirms token registration, a test push, foreground display, background display, and tap routing.
* **AC-17**: Before queueing an automatic event push, the Backend saves a durable receipt with the normalized event type, a server selected template version, recipient user ID, and deterministic in app notification ID. Supported automatic templates are fixed server owned copy, so this receipt data is sufficient to rebuild the notification and push without reading the original order or account record. If the in app notice is missing while its receipt is pending and being recovered or replayed, recovery recreates it with the same ID and owner permissions before continuing delivery. An accepted receipt is not used to recreate a notice later, so a notice cleared after delivery stays cleared. Receipts do not store rendered message text, raw event payloads, push tokens, or sound IDs. The Backend keeps each referenced template version available for at least 365 days after the last receipt is created with that version. An unsupported version or invalid receipt is marked unresolved and is not sent. Push eligibility and sound are resolved from current account preferences at each delivery attempt.
* **AC-18**: Notification Settings lets customers control order, promotion, reward, and app or service update pushes. Order, reward, and app or service update pushes default on. Promotion push consent defaults off and remains represented by the indexed top level `marketingPushEnabled` field; there is no second promotion consent value. Security and welcome pushes stay enabled and cannot be turned off in the app. These settings affect push only. Existing in app notices remain available when a category push setting is off. Other existing product, vendor, support, and AI notification preferences remain unchanged and are not added to this settings panel.
* **AC-19**: Each controllable category has its own sound choice from its assigned bundled sound group, plus a silent choice. The first numbered WAV choice is the default. Order uses CoreFlow, promotion uses Kalimba, reward uses Nile Miles, and app or service updates use Sonic logo. Security and welcome use the first CoreFlow sound. Customers can preview bundled choices in the app using `expo-audio`; preview is an explicit user action, ignores the push master mute, respects device audio settings, and does not request microphone permission or background audio.
* **AC-20**: Category push settings, selected sound IDs, and master mute are stored with the existing `notificationPreferences` object on the Appwrite user document and are returned and updated through the authenticated notification preferences API. Promotion consent and its timestamp remain in their existing top level fields. Preferences sync across devices. If the account has no `soundMuted` value on first sync, a locally saved legacy mute value is copied to the account; if neither exists, master mute defaults off. An existing account value wins, and later syncs use the account value. Unknown category keys, push values, and sound IDs are rejected by the Backend.
* **AC-21**: The app registers stable Android channels for every supported category and sound choice before push delivery, including locked security and welcome channels and the existing default channel for other notification types. The Backend selects the channel from the authenticated user's category sound choice and master mute. Master mute selects a silent channel for every customer push type. It never tries to change the sound of an existing channel. A changed sound asset receives a new sound ID and channel ID. iOS push payload sounds use the same bundled sound registry, and set `sound` to `null` when the category is silent or master mute is on. A user's operating system channel or notification settings remain authoritative.

## Decision

**Chosen option**: Option 1, strengthen the existing Expo and BullMQ path and extend it for admin campaigns.

Keep Appwrite as the record store, Expo as the mobile push provider, and the existing BullMQ queue as the background worker. Use one centralized Expo sender for automatic events and admin broadcasts. Add explicit consent, durable campaign records, restricted delivery records, and aggregate reporting. Roll out the automatic event path and campaign feature in controlled steps.

The campaign recipient snapshot is built by a paged worker from user records whose first token registration is no later than the snapshot. The preview shows two estimates: users with a recorded `pushTokenFirstRegisteredAt` in the in app audience, and the subset currently eligible for push under token, category, and consent settings. The worker records the final candidate count when it materializes recipients. Push settings and promotion consent are checked immediately before push delivery, not before the in app notice is created.

`recipientSnapshotAt` is set once when a worker first claims the campaign. Candidate users are read in ascending Appwrite document ID order when `pushTokenFirstRegisteredAt` is no later than that timestamp. Before expiry, the worker creates the in app notice for each candidate. It then checks the current token and category push setting. Promotion push additionally requires `marketingPushEnabled` and a consent timestamp no later than the snapshot. A missing token, disabled category, missing consent, or later consent marks only the push outcome skipped. Users who become eligible after the snapshot do not join that campaign, while a later opt out can still stop a send. If the campaign has expired before processing a candidate, the worker skips the recipient without creating an in app notice.

The Backend sets the campaign's immutable `expiresAt` at creation: promotion is 24 hours, app update is 30 days, and service announcement is 7 days. Before first processing each recipient, the worker compares the current UTC time with `expiresAt`. At or after the deadline it marks the recipient skipped without creating an in app notice. Before the deadline it creates the notice and sends the remaining lifetime as the Expo message TTL, so queued pushes do not remain deliverable beyond the campaign deadline. If a later retry or recovery reaches the deadline, it skips the push and retains any notice already created before expiry.

**Admin UI direction**: Add the Broadcasts tab within the existing Notifications page and match its visual style and page structure.

**State transitions**:

* Campaign: `queued` → `sending` → `complete` or `complete_with_issues`. Completion waits until every candidate has terminal in app and push outcomes. Any unresolved outcome completes with issues.
* Campaign cancellation: `queued` → `cancelled`. Cancellation is rejected once processing starts.
* Campaign push delivery: `pending` → `accepted`, `rejected`, `unresolved`, or `skipped`. `accepted` means Expo returned an accepted ticket, not that the device displayed the message.
* Campaign in app notice: `pending` → `created`, `unresolved`, or `skipped`. In app counters for these terminal states add up to the final target. Push state and in app notice state are tracked separately.
* Automatic event receipt: `pending` → `accepted`, `rejected`, `unresolved`, or `skipped`. A replayed event with an existing receipt reuses it and never creates a second in app notice.
* A queued campaign includes recipient preparation. In app notification records are created only as recipient processing starts, so cancelling before processing does not leave unread campaign notices behind.

The AdminDashboard creates one UUID v4 idempotency key for each send intent and reuses it for transport retries. The Backend trims surrounding whitespace, preserves internal body whitespace and paragraph breaks, normalizes the route to null when absent, and hashes the canonical JSON object containing title, body, category, and route. The hash is compared on an idempotent replay. Campaign audience candidates remain in the in app audience even when they cannot receive a push.

The campaign create request stores the campaign and both estimates before queueing. A retry with the same key returns that same campaign. If queueing fails after the record is saved, the API returns 503 with the campaign ID and explicitly says it was saved but not queued. A recovery scan runs every 30 seconds. It enqueues queued campaigns with no live job and resumes sending campaigns from their saved cursor when the deterministic page job is missing or failed. BullMQ handles stalled active jobs. The API never returns a queued success unless Redis accepts the job.

| Send order update | Server owned title, body, route, and event key | Normalized order confirmation from successful payment or accepted cash on delivery, later order state transitions, cancellation request receipt or decision, and the resulting Backend event type |
| Send account security alert | Server owned title, body, route, and event key | Successful password or email change operation; the Backend creates an operation ID when the change succeeds |
| Recover automatic notification | Title, body, route, notification type, and metadata | Server owned template renderer selected by the receipt's normalized event type and `templateVersion`; recipient ID and deterministic notification ID come from the receipt. Recovery does not read the source order, account, or operation record. |
| Deduplicate automatic event | Event receipt ID and queue job ID | SHA 256 hash of the stable event key plus recipient user ID; order ID and normalized event type/state, cancellation request ID and decision, welcome user ID, or account change operation ID. The server selects `templateVersion` when creating the receipt. |
| Route push tap | Internal app route or notification list fallback | Validated campaign route in notification data, otherwise existing app notification route |
| Unregister device | Current token removal | Authenticated logout or OS permission status checked when the app resumes |

**Key invariants**:

* Expo is the sole mobile push provider. Appwrite Messaging remains available for its existing email and SMS uses, but its push sender is not also invoked for these events.
* All push sends run through the existing `nf:notifications` worker. Use bounded exponential retries, with the queue's existing five attempt policy. A provider timeout with no ticket is ambiguous, so automatic retry can result in a duplicate.
* `DeviceNotRegistered` clears the matching current user token. Appwrite lookup errors are failures to retry, not proof that a user has no token.
* Appwrite campaign, delivery, and event receipt records remain the source of truth. A recovery scan requeues pending campaigns and event receipts if the process stops between database writes and Redis enqueue. Campaign workers save one `recipientSnapshotAt`, read users in ascending document ID order using `pushTokenFirstRegisteredAt`, and use `lastProcessedUserId` as the stable cursor. Advance the cursor only after every candidate in the page has a durable delivery row. Before starting another page, process any existing pending delivery rows. If processing stops first, repeat the page and reuse its unique campaign plus user records.
* One shared Redis lock per campaign protects worker start, cancellation, and manual retry. The lock is released with a token checked delete. A cancellation wins only if it obtains the lock while status is still queued; otherwise it returns conflict.
* Campaign locks have a 30 second lease renewed every 10 seconds while held. If a lock is busy, cancel and retry return 409 and leave campaign and delivery state unchanged.
* Automatic event receipts use a unique hash of the stable event key and recipient user ID. Create the receipt and in app notification idempotently before queueing. The receipt stores the normalized event type and server selected template version, recipient user ID, and deterministic notification ID. These values resolve to the immutable server owned copy and route, so recovery can recreate the notice without the source order, account, or operation record. The supported automatic templates contain fixed copy and require no dynamic event values. If a notice is missing while its receipt is pending and being recovered or replayed, recreate it with the same deterministic ID and owner permissions before continuing delivery. Do not recreate a notice for an accepted receipt, because a customer may have cleared it after delivery. Never store rendered title or body, raw event payloads, or a token in the receipt. Keep each referenced template version available for at least 365 days after the last receipt is created with that version. If a receipt is invalid or references an unavailable template version, mark it unresolved, do not send, and emit an operational error without logging message content or recipient details. If Expo may have accepted a push but the worker did not save the acceptance, recovery retries the pending receipt and accepts the small duplicate risk rather than silently losing delivery. Campaign in app notices also use deterministic IDs derived from their delivery rows. Retain compact event receipts for one year.
* Retain the normalized payload hash with the campaign. Idempotency keys are UUID v4 values generated once per admin send intent; the same key with the same canonical payload returns the same campaign, while a changed payload returns conflict.
* Campaign delivery counts are based on each recipient's current delivery state. A manual retry changes a transient rejected row to pending, then to its latest result. It never increments an accepted or unresolved row. A row can receive only one manual retry, with up to five additional automatic attempts. Expired campaign recipients are skipped, and an expired push is not eligible for manual retry. An in app notice created before expiry remains visible even when a later push retry is skipped as expired.
* A daily BullMQ retention job deletes campaign delivery rows and automatic event receipts older than 365 days. It does not delete campaign content or aggregate counts.
* Production must use durable Redis. The in memory fallback is not acceptable for push delivery. Do not accept new admin sends when the durable queue is unavailable.
* The estimated audience may differ from the final audience. Final push outcome counts sum to the final target. Pending is derived from the target and push outcome counts only after the recipient snapshot is complete. An in app notice can be created for a recipient whose push is skipped.
* Existing users have no promotional consent until they explicitly opt in. Legacy `notificationPreferences.promotion.push` values are not considered consent. `NotificationPreferences` must use `marketingPushEnabled` for promotion pushes and must not fall back to a legacy enabled default. Promotional consent and category settings control push only, not the creation of an in app notice for an existing campaign candidate.
* Order, reward, and app or service update push settings default on. Promotion push defaults off. Security and welcome pushes remain enabled regardless of these category settings. Product, vendor, support, AI, and other existing event types keep their current preferences and default sound, are not added to the customer settings panel, and are not silently mapped to a customer controlled category. The global mute still suppresses their push sounds.
* Normalize reads of `notificationPreferences` without overwriting email, SMS, WhatsApp, or in app settings. Updates merge only the allowed nested fields. Persist sound choices by stable sound ID, never by client supplied file path.
* Android channel IDs include category and sound ID. Create every supported channel before a push can target it, including each category's silent channel. Do not attempt to change an existing channel sound. The master mute selects the silent channel. Android operating system controls can still mute or alter any channel.
* iOS push sound names and in app preview sources come from the same bundled sound registry. A new asset must use a new sound ID so existing Android channel IDs are never silently repurposed.
* A single `pushToken` field supports only the latest registered device for a user. Multi device token registration is out of scope. `pushTokenFirstRegisteredAt` is set on first registration, retained when a token is removed, and backfilled for existing registered users.
* Validate category, text lengths, the exact route allowlist, pagination, UUID v4 idempotency keys, and normalized payload hash on the Backend. Reject query strings, fragments, external URLs, dynamic path values, and unlisted routes. Apply the existing API rate limiting and audit logging.
* Campaign, delivery, and automatic event receipt records are service only. In app notice documents remain readable and manageable only by their owning users.

**Security model**:

* Every admin endpoint verifies the signed in session and requires `req.user.role === "admin"`. A second admin approval is not required.
* Customer preference endpoints derive user identity from the verified session and accept no user ID or client timestamp. They reject locked security and welcome settings and any sound ID outside the server allowlist.
* The Backend validates all campaign inputs and accepts only internal app destinations. The AdminDashboard never receives delivery user IDs or tokens.
* Record the acting admin, campaign ID, category, action, timestamp, and aggregate results in the existing audit path. Do not log push tokens, raw provider payloads, or recipient level delivery data.
* Use server only Appwrite access for campaign, delivery, and event receipt collections. User notification documents retain owner scoped permissions.

**Configuration required**:

* `REDIS_URL`: existing production Redis connection, required for durable campaign and event work.
* `APPWRITE_PUSH_BROADCASTS_COLLECTION_ID` and `APPWRITE_PUSH_BROADCAST_DELIVERIES_COLLECTION_ID`: IDs for the new service only collections.
* `APPWRITE_PUSH_EVENT_RECEIPTS_COLLECTION_ID`: ID for the private automatic event receipt collection.
* `PUSH_NOTIFICATIONS_V2_ENABLED`: rollout flag. Keep new sends disabled until schema, worker, and physical device checks pass.
* EAS Android FCM V1 and iOS APNs credentials: user reports these are configured. Verify them during release validation.
* Android Firebase client configuration: provide `google-services.json` for package `com.nileflowafrica` and reference it from Expo Android config if it is not already configured. This is separate from the private FCM service account key.
* `expo-audio`: add the Expo compatible package for local sound preview. Configure playback only, with no microphone permission or background audio mode. Register notification sound assets with the existing Expo notifications native build configuration.

## Consequences

**Positive**:

* Automatic alerts and admin broadcasts share one observable, retryable mobile delivery path.
* Admins can communicate to mobile users without using newsletter email delivery, and customers control promotional consent.
* Customers control push categories and sounds with account synced preferences. Promotional push opt out no longer hides the related in app campaign notice.
* Persistent campaign state supports recovery, honest reporting, and safe manual retry.
* Stable event receipts prevent repeated business events from generating duplicate alerts during the one year retention period.

**Negative / tradeoffs**:

* Appwrite schema, indexes, a recovery worker, and production Redis operations add work.
* One user document stores one current push token, so only the latest registered device receives pushes.
* Expo acceptance is not proof of display. Ambiguous timeouts can create rare duplicates despite idempotent Backend handling.
* Promotional pushes reach fewer devices until users explicitly opt in, while in app notices remain available to campaign candidates.
* Campaign locks, snapshot fields, event receipts, and retention work add operational code and private records. Event deduplication ends when its one year receipt is removed.
* Custom audio adds bundled assets, native build configuration, Android channel maintenance, and cross platform device testing. Android users can override each channel in operating system settings.

**Neutral**:

* EAS credentials alone do not trigger notifications. Users still need an installed native build, permission, a registered token, and a Backend event or admin send.
* Admin broadcasts are immediate only. Scheduling, audience segments, recipient level reports, and multi device token storage remain out of scope.

## Migration plan

**Strategy**: Feature flagged strangler rollout, replace one push path at a time while retaining existing non push channels.

**Phases**:

1. Add nullable user attributes, campaign snapshot and cursor fields, and new collections and indexes. Backfill first token registration timestamps for existing tokens. Deploy migrations before code that writes them. Missing marketing consent means false. Mark all pre existing users as already welcomed. Do not add a notification preference collection; normalize the existing user preference object and preserve unrelated channel settings.
2. Deploy the Expo sender, campaign worker, and APIs with `PUSH_NOTIFICATIONS_V2_ENABLED` disabled. Confirm Redis, EAS credentials, Android client configuration, and physical device delivery in staging.
3. Move one automatic event at a time to the Expo queue and disable its legacy Appwrite push call. Preserve email, SMS, WhatsApp, and in app delivery. Watch ticket errors and duplicate reports before expanding.
4. Release the Mobileapp preference and sound registry after verifying local mute migration, account sync, bundled asset registration, and Android channel creation on physical devices.
5. Enable admin broadcasts after customer consent, preview, queue recovery, and separate in app and push reporting pass staging checks.

**Rollback**: Disable new campaign creation first. Keep workers running to finish or safely pause already accepted campaigns. Do not replay processed event keys through the legacy provider. If the automatic path must roll back, route each event to exactly one provider and verify no queued Expo event is also sent through Appwrite.

**Risks**: Appwrite and Redis cannot commit atomically, so the campaign recovery scan is required. A feature flag change must not strand accepted work. Existing Appwrite schemas may need an additive migration before the app and Backend can use the new fields.
